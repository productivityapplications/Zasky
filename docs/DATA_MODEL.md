# Zasky — Data Model Reference

SQLite is authoritative. Store UTC instants as ISO-8601 UTC; store planning dates as `DATE` interpreted in the owner's IANA timezone. UUIDs are generated by the application. Use foreign keys, indexes and transactions described below.

## 1. `owner_config`

Singleton row; primary key `id` (integer, fixed value `1`).

| Field | Type | Required | Default / constraints |
|---|---|---:|---|
| `owner_switch_participant_id` | TEXT | Yes | Exact opaque Switch participant ID; unique |
| `allowed_room_id` | TEXT | Yes | Exact allowed room |
| `timezone` | TEXT | Yes | Provisional `Africa/Lagos`; valid IANA zone |
| `capacity_pct` | INTEGER | Yes | 65; CHECK 60–70 |
| `week_start_weekday` | TEXT | Yes | Operator-confirmed weekday; Monday recommended |
| `daily_task_limit` | INTEGER | Yes | 3; fixed product limit |
| `transition_buffer_min` | INTEGER | Yes | 10 candidate; non-negative |
| `morning_prep_min` | INTEGER | Yes | 30 candidate; non-negative |
| `commute_buffer_min` | INTEGER | Yes | 0 only if operator confirms; non-negative |
| `availability_json` | JSON/TEXT | Yes | Owner-supplied weekday windows; validated schema |
| `morning_prompt_time` | TEXT | Optional | Candidate `07:00` local |
| `evening_prompt_time` | TEXT | Optional | Candidate `20:00` local |
| `reminders_enabled` | BOOLEAN | Yes | false until operator enables |
| `timebox_checkins_enabled` | BOOLEAN | Yes | false until operator enables; SHOULD HAVE |
| `revision` | INTEGER | Yes | starts at 1; increment on relevant configuration change |
| `created_at`, `updated_at` | DATETIME | Yes | UTC |

No secret key belongs in this table. Secrets are environment/secret-store values.

## 5. `week_placements`

Links a month commitment to a particular week. One commitment can have multiple placements across weeks. A placement is a weekly container; individual work items carry their own dates so reconciliation can move one item without moving every task under the commitment.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID TEXT | Yes | PK |
| `commitment_id` | UUID TEXT | Conditional | FK `month_commitments.id`, RESTRICT; required for normal placements, null only for explicit ad hoc |
| `source_type` | TEXT | Yes | `commitment` or `ad_hoc`; `ad_hoc` requires explicit owner flag |
| `week_start` | DATE | Yes | configured week-start date (Monday recommended; confirm at intake) |
| `status` | TEXT | Yes | `active`, `completed`, `cancelled`; default active |
| `revision` | INTEGER | Yes | starts 1 |
| `created_at`, `updated_at` | DATETIME | Yes | UTC |

Index `(week_start,status)`, `commitment_id`. Add a CHECK constraint so `commitment_id IS NOT NULL` when `source_type='commitment'` and `commitment_id IS NULL` when `source_type='ad_hoc'`. Add a partial unique index on `(commitment_id, week_start)` for non-null commitment IDs so each commitment has at most one placement container per week. The week-start convention is fixed at intake; every task's `scheduled_date` must fall within that week. One `place_week` proposal containing multiple commitments is grouped into one row per commitment; commitment-free ad hoc work is grouped into an ad hoc row.

## 6. `week_tasks`

Concrete work units in the approved weekly pool.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID TEXT | Yes | PK |
| `placement_id` | UUID TEXT | Yes | FK `week_placements.id`, RESTRICT |
| `title` | TEXT | Yes | 1–200 chars; exact owner-provided task |
| `est_min` | INTEGER | Yes | > 0 |
| `scheduled_date` | DATE | Yes | must fall within parent placement's `week_start` week |
| `status` | TEXT | Yes | `active`, `parked`, `completed`, `cancelled`; default active. `cancelled` is set only by an approved parent commitment cancellation; there is no standalone task-cancel command. |
| `resume_note` | TEXT | No | required when parked, max 1000 chars |
| `actual_min` | INTEGER | No | >= 0; owner supplied |
| `ad_hoc` | BOOLEAN | Yes | false; true only after explicit owner ad hoc flag; must match parent placement source type |
| `created_at`, `updated_at` | DATETIME | Yes | UTC |
| `completed_at` | DATETIME | No | UTC |

Indexes `(placement_id,status)` and `(scheduled_date,status)`. Task may appear in multiple historical day plans but only once in a given plan. Reconcile moves a task by updating its `scheduled_date` after approval. Parked/completed/cancelled tasks are excluded from new day plans. A normal `plan_day` only selects tasks with `scheduled_date` exactly matching the requested local date; overdue tasks are considered only through an approved `reconcile` proposal.

## 10. `processed_switch_events`

| Field | Type | Required | Rules |
|---|---|---:|---|
| `agent_id` | TEXT | Yes | Registered Switch agent ID |
| `event_sequence` | BIGINT | Yes | Numeric sequence from WebSocket event envelope; composite PK with agent ID |
| `connection_id` | TEXT | Yes | Stable Switch connection ID |
| `room_id` | TEXT | Yes | Exact room ID |
| `sender_id` | TEXT | No | opaque participant ID |
| `message_id` | TEXT | No | opaque message ID |
| `outcome` | TEXT | Yes | `ignored`, `replied`, `proposal_created`, `approval_applied`, `failed` |
| `processed_at` | DATETIME | Yes | UTC |
| `correlation_id` | TEXT | Yes | internal opaque ID |

Composite primary key `(agent_id,event_sequence)`. Do not store raw message body. Switch WebSocket domain event `id` is a JSON number equal to its `sequence`; use that numeric sequence as the idempotency key for the registered agent. Retention can be bounded after verified cursor/replay semantics, but keep enough to prevent replay during the supported recovery window.

## Data visibility rules

- Public: none.
- Owner only: all goals, commitments, fixed events, availability, tasks, estimates, deadlines, consequence, battery, resume notes, proposals, plans and history.
- Operator infrastructure only: host identifiers, backup paths, redacted logs, cost/health status.
- Secrets: separate protected secret store/env file; never in SQLite, prompt, audit or demo data.


## 13. `model_usage_records`

Required for budget controls and auditability.

- `id` UUID PK
- `provider` TEXT (e.g. `openai`)
- `provider_request_id` TEXT UNIQUE when available
- `model` TEXT
- `pricing_version` TEXT/date or identifier for the price schedule checked at intake
- `input_tokens` INTEGER >= 0
- `output_tokens` INTEGER >= 0
- `reserved_cost_microusd` INTEGER >= 0; worst-case reservation created before provider request
- `actual_cost_microusd` INTEGER nullable >= 0; populated from verified provider usage
- `status` TEXT `succeeded|failed|unknown`; unknown usage keeps reservation held until reconciled
- `occurred_at` DATETIME UTC
- `correlation_id` TEXT

Index by `occurred_at` for monthly aggregation. Store minimal usage metadata only; do not store raw prompts or full model responses in this ledger. Before sending a provider request, calculate an upper-bound cost using the bounded input-token count, configured maximum output tokens and intake-verified price schedule; reserve that amount transactionally. Reject a request if committed cost plus outstanding reservations would exceed the monthly ceiling. After a response, settle to actual usage. On timeout/unknown provider outcome, keep the conservative reservation until reconciled. Provider price changes require an operator-approved configuration/price update and a documented effective date.


## 14. `switch_connection_state`

One row per registered Zasky agent.

- `agent_id` TEXT PK
- `connection_id` TEXT UNIQUE (stable UUID reused on reconnect)
- `generation` TEXT/INTEGER using the exact type returned by Switch
- `highest_processed_sequence` BIGINT >= 0 (Switch sequences can exceed signed 32-bit)
- `protocol_revision` TEXT/INTEGER as returned
- `last_connected_at` DATETIME UTC
- `updated_at` DATETIME UTC

Persist the `connection_state` frame before processing domain events. On reconnect, use the same connection ID, highest processed numeric sequence as `start_from`, and `expected_generation` from the last valid connection state. A gap/restore requires following the current Switch recovery contract before advancing the cursor.


## 15. `timebox_checkins` (SHOULD HAVE)

Only implement after the core reconcile loop passes E2E.

- `id` UUID PK
- `session_key` TEXT UNIQUE (idempotent scheduler key)
- `checkin_type` TEXT `task_overrun|panic_10m`
- `task_id` UUID nullable FK `week_tasks.id`
- `day_plan_item_id` UUID nullable FK `day_plan_items.id`
- `due_at` DATETIME UTC
- `status` TEXT `pending|sent|cancelled|skipped`
- `sent_at` DATETIME nullable UTC
- `created_at` DATETIME UTC

Unique `session_key`; index `(status,due_at)`. A pending task-overrun check-in is cancelled if its task is completed/parked before due time. No task state changes happen merely because a check-in is sent.


## 16. `planning_scope_revisions`

Generic optimistic-concurrency ledger used to stale proposals reliably when any relevant source record changes.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `scope_key` | TEXT | Yes | PK; canonical scope such as `goal:2027`, `month:2027-01`, `week:2026-11-02`, `day:2026-11-05`, or `commitment:{uuid}` |
| `revision` | INTEGER | Yes | Starts at 1; increments monotonically on every committed mutation affecting that scope |
| `updated_at` | DATETIME | Yes | UTC |

Create missing scope rows transactionally with revision 1. Proposal creation records the relevant scope/revision pairs in its payload and primary `scope_key`/`base_revision` columns. The approval transaction locks/serializes the write, compares all expected revisions, performs the domain mutation and increments the affected scopes atomically. A mismatch marks the proposal `stale`; no partial write occurs. Mutations to a task status/date increment its week scope and, when applicable, its assigned day scope. A fixed-event change increments each affected week/day scope whose schedule overlaps the event. Owner configuration changes increment `config:owner` and invalidate any proposal whose calculation depended on changed settings.

## 18. `delegation_proposals`

Human-in-the-loop delegation records for the Execution Sub-Agent.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | UUID TEXT | Yes | PK |
| `code` | TEXT | Yes | Unique owner-facing proposal code (`ZK-XXXX`) |
| `task_id` | UUID TEXT | Yes | FK `week_tasks.id` RESTRICT |
| `status` | TEXT | Yes | `pending`, `running`, `awaiting_signoff`, `completed`, `rejected`, `expired`, `failed` |
| `execution_code` | TEXT | No | Unique second code for owner sign-off (`ZK-YYYY`) |
| `output_markdown` | TEXT | No | Structured three-section sub-agent deliverable |
| `error_code` | TEXT | No | Bounded failure code |
| `created_at` | DATETIME | Yes | UTC |
| `expires_at` | DATETIME | Yes | Pending delegation TTL |
| `resolved_at` | DATETIME | No | UTC |
| `resolution_actor` | TEXT | No | Owner actor ID |

The table is written by deterministic application code, never by the model.
`delegate ZK-XXXX` moves a pending record to `running` and creates the execution
code. The sub-agent output moves it to `awaiting_signoff`. Only
`approve execution ZK-YYYY` completes the task and marks the record `completed`.
